# 《问道长生》声音系统技术规格

规格先行，本文件不包含实现代码。排期见 [roadmap.md](./roadmap.md)：**BGM/SFX 为 F1**（可在阶段 B 末做气氛，不得推迟成册）；**人声为 F5**。声音系统是独立子系统：负责通道混音、配乐切换、旁白 / 天道 / NPC 语音播放；不负责撰写剧情或计算数值。数值与剧情铁律见 [game_design.md](./game_design.md)。代码架构见 [audio_architecture.md](./audio_architecture.md)。

剧情入口为 `MainGame.tsx` 的 `LogEntry`（`system` / `player` / `narrative`）。NPC 姓名来自 `player_relationships`。天道文案来自后端 `forcedOutcome` 与系统日志。

## 7. 技术答疑（对应你的疑惑）

### 7.1 RVC + 网上公开原声，可行吗？

**可行，但是「后期服务器方案」，不是网页小功能。**

RVC（Retrieval-based Voice Conversion，常见仓库 [RVC-Project/Retrieval-based-Voice-Conversion-WebUI](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI)）做的是：**已经有一段人声**，再把它的「嗓音」换成你训练好的那个人。它 **不会** 从汉字直接出声。所以完整链是：

1. TTS（浏览器语音 / Edge-TTS / CosyVoice 等）把「台词字」变成普通人声；
2. RVC 把这段人声变成「天道腔 / 某 NPC 腔」。

为什么第一期不能用 RVC：

- 推理要 Python、模型和最好有 GPU，体积几百 MB 起，塞不进现在的 React+Vite 前端。
- 每个目标音色要一份模型；你为每个新 NPC 现训一个模型，成本和等待都不可接受。
- 「网上公开原声」训练出的模型，声音权通常仍属于原说话人。游戏若上线，这和「随便下个 mp3 当 BGM」一样，有下架和侵权风险。开发自测可以玩，**当上线素材不行**。

结论：想法对（AI 变声很适合修仙腔），分期做：先让游戏能出声 → 再换更好听的 TTS → 最后用 **你自己授权或自制** 的 RVC 模型当皮肤。

### 7.2 新 NPC「AI 调配合适声音」，GitHub 有什么？

没有「输入角色小传，自动吐出一个独一无二、可商用、还在浏览器里跑的声线」的现成库。能组合的开源方向：

| 用途 | 常见仓库 | 说明 |
|------|----------|------|
| 变声 | RVC-WebUI、[w-okada/voice-changer](https://github.com/w-okada/voice-changer) | 要源音频+模型，偏本地/服务端 |
| 音色迁移 | [myshell-ai/OpenVoice](https://github.com/myshell-ai/OpenVoice) | 一段参考音克隆音色，仍是服务端 |
| 中文 TTS | CosyVoice、ChatTTS、Fish Speech、GPT-SoVITS | 多说话人 ID，适合「声线库」而不是一人一模 |
| 网页朗读 | 浏览器 Web Speech（第一期） | 免费，音质一般，够打通流程 |

**推荐的「每人固定」实现（第二期，不必等 RVC）：**

准备 8～20 条合法声线（不同性别、年龄感、冷热）。`hash(npc_name)` 对库大小取模，得到编号。同一名字永远同一编号 = 「每人固定」；新结识的人立刻有声，不用训练。以后真要「更适合」，可以让你或运营在表里把该名字改绑到另一编号（人工调配），而不是让模型现训。

「AI 调配」若指 **让 DeepSeek 根据 NPC 描述选库内标签**（如「冷清女声」），这只是选编号，可以做；它 **不能** 在没有后端算力时现场炼一个新 RVC。

### 7.3 缓存 / IndexedDB 是什么？要不要上传服务器？

浏览器朗读（第一期）是操作系统当场念，**没有 mp3 文件**，所以没有「缓存音频」这一步。

若以后 TTS 返回一段音频：

- **IndexedDB / Cache Storage**：存在 **这台电脑的这个浏览器** 里，下次同一句同一音色可以少请求一次，省钱、省等待。数据在玩家家里，不是你的机房。
- **上传到你们服务器**：把音频文件 POST 到你的网站。你说目前没有自己的服务器，就 **不要做上传**。也不要把 wav 塞进 MySQL。

和「有没有服务器」的关系：没有服务器，你仍然可以做单机网页游戏（现在这样）；只是 **不能** 把「只有你知道的 API 密钥」藏起来给所有玩家用（见下）。

### 7.4 什么是后端代理？为什么第一期可以没有？

现在朗读走浏览器，BGM 是你放在 `public/` 里的文件，**不需要任何语音 API 密钥**，所以第一期纯前端成立。

一旦使用「云 TTS、云 RVC、或任何按量付费的 AI 语音」：

- 密钥若写在前端 JS 里：任何人打开开发者工具就能复制，拿去刷到你账单爆掉。
- **后端代理** = 浏览器只向你的 Express 说「请朗读这句」；真正带密钥去找微软/讯飞/自建 RVC 的是 `backend`，密钥放 `.env`（已规定不进 Git）。

你没有单独云主机时，**本机已经在跑的 Express（`backend/server.ts`）就可以当这个代理**。这不是必须再买一台机器；是「密钥不要离开服务器进程」。没有这层，就不要把个人 TTS Key 发给网上每一个玩家。

### 7.5 上线、商用、用我的 API 怎么回本？

详见 [project_status.md](./project_status.md) 第 5–7 节（含 RVC 是否免费商用、20 条声线从哪找、公开 GitHub 的影响、L0–L3 上线方案）。

分三层，不要混在一起：

1. **现在（开发能否玩）：** 用 CC0/无版权 BGM + 浏览器朗读。不花钱，可以验证系统。不能把网易云/B 站扒的歌推进 Git。
2. **以后若上线（Steam、网站、给陌生人玩）：** BGM 需要许可或自制。RVC 要用你有权的声音。DeepSeek 和 TTS 若仍是 **你的 Key**，每一个玩家点一下都在花 **你的钱**。
3. **回本（商业问题，不是混音器问题）：**  
   - 买断/内购/广告：你出算力，玩家付钱；必须有后端限额，否则被刷。  
   - 玩家自备 Key（填自己的 DeepSeek/TTS）：你几乎 0 成本，但门槛高。  
   - 完全本地（浏览器语音 + 本地 RVC）：你无 API 账单，音质看玩家电脑。  

「先能上线再谈商用」时，技术上仍建议：**上线通道不要默认绑定你的私人额度**。游戏逻辑可以上线；语音可以做成「可选：浏览器声 / 玩家自己的 Key / 日后付费高清」。
